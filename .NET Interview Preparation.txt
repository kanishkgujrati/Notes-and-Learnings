What are variable types in .Net - Value Type & Reference Type
	-> Value Type - Stack Object, Hold Values, (Enums, Struct, int, char)
		They are commonly stored on the stack when used as local variables.
	-> Reference Type - Heap Object, Holds Pointers(References) to heap obj, (String, Array, Class, Interface, Pointers, Delegates)

CORS - Cross Origin Resource Sharing Policy  (*Browser Security*)  (❌ Backend security ❌ Network security ❌ Authentication)
	A browser security mechanism that controls or allows a server to specify which origins are permitted to access its resources. Applied on the API (Server) Application.
	'Same-Origin Policy' (SOP) is a browser security rule that prevents JavaScript from reading data from a different origin.
	
		Origin = Scheme + Host + Port   -  https://example.com:443
						     │        │        │
						    scheme   host     port
		
		Same Origin example  - Frontend: https://app.example.com  && Backend: https://app.example.com/api/users
		Cross Origin example - Frontend: https://app.example.com && Backend: https://api.example.com/users           -- Cross-origin request. CORS rules apply.
	
	*CORS does not block requests from being sent. CORS controls whether the browser allows Client to read the response or not.
		If Client does not have access, the response will EXIST but the client wont be able to see or access it.
	
	Only for Client <-> Server (U2M) calls, Not for Server <-> Server (M2M), as CORS is Browser Security.  (Postman does not enforce browser security policies.)
	
	app.UseCors(); - This Middleware actually adds CORS Headers to each Request and Response.  After this Middleware we are supposed to have UseAuthentication(); and UseAuthorization(); in the Request Pipeline.
	builder.Services.AddCors(options =>
	{
		options.AddPolicy("MyPolicy", policy =>
		{
			policy
				.WithOrigins("https://app.example.com")
				.AllowAnyMethod()
				.AllowAnyHeader();
		});
	});

Why does CORS exist ? -> Imagine you are Logged in to your bank. Now you visit some other website. The browser would send your cookies automatically. Other Website could read all your bank related data.
	CORS prevents other websites from reading the response.
	If you have multiple website open on different tabs in your browser, each tab will have access to data and cookies or storage of all the other tabs.
	
For allowing CORS, Server adds ->  Access-Control-Allow-Origin: https://app.example.com  - this Header to the HTTP response.
Now Response would look like  ->  HTTP/1.1 200 OK Access-Control-Allow-Origin: https://app.example.com    (CORS Header)
									Origin matches. Allow JavaScript access to read the response.
	Access-Control-Allow-Origin
	Access-Control-Allow-Methods: GET,POST,PUT,DELETE
	Access-Control-Allow-Headers: Authorization,Content-Type
	Access-Control-Allow-Credentials: true           (Cookies with CORS)

Public APIs have -> Access-Control-Allow-Origin: *      ---- Any origin can read this response.

Middleware :- It is a component in ASP .Net Core, HTTP Request and Response pipeline.
	It processes each incoming HTTP request, can handle, modify and forward req to the next Middleware.
	Middleware is commonly used for Logging, Authentication, Authorization and Error/Exception Handling.

	Configured in the Configure() of Startup.cs
	app.UseCorsPolicy(), app.UseAuthentication(), app.UseLogging(), app.UseHttpRedirection(), app.UseRouting();

Request Delegates - Actual Fn that Handles/Controls the flow of each Http Request from one middleware to another.     public delegate Task RequestDelegate(HttpContext context);
	Request Delegate is a function that takes an HttpContext object (which holds the Http Request and Response and returns a Task. 
When an HTTP request hits your server, .NET wraps the raw request into an HttpContext and passes it to the first Request Delegate.

-> Use() - The Inline/Chaining Delegate - After executing itself, It will execute the next Middleware in the pipeline. eg - app.UseAuthentication, app.UseCorsPolicy
-> Run() - The Terminal Delegate (LAST) - There is no Middleware execution after this, It is always the Last Execution in the Request Pipeline. eg - app.Run()
-> Map() - The Branching Delegate - Split the pipeline into branches based on the request's URL path. 
			If the incoming request matches the path specified, .NET reroutes the request into a completely separate mini-pipeline containing its own set of delegates.
-> MapWhen(),  UseWhen()

There is a sequence, Each Middleware plays its part on the request and passes it to the next middleware.

HTTP Request -> Middleware1 -> Middleware2 -> Middleware3 -> Endpoint -> Response
	Then Response travels backward.

Terminal and Non-Terminal Middleware
	Terminal Middleware does not have await next() in the implementation. It ends the pipeline (app.UseEndpoints(), app.Run())
	Non-Terminal Middleware calls the next delegate to pass the control to the next Middleware in the pipeline.

Custom Middlewares can be used in another Apps as well.
	Create Nuget Package of the Custom middleware and add an extension method like public static class.
	return builder.UseMiddleware<CustomMiddleware>();

	Eurofins we used services.AddTransactionLogServices(configuration)  for the Transaction/Performance Logging.

Always use await _next(); in the Middleware to prevent breaking the middleware pipeline.

Dependency Injection - It is a Design Pattern that allows objects to recieve their dependencies from an external source, rather than creating them itself.

In .Net core we have Buil-in DI, helps promote Loose Coupling Designs and Maintainable Code.

Services are registered in ConfigureServices using AddSingleton(), AddScoped() and AddTransient(). (In Startup.cs or Program.cs)
	builder.services.AddSingleton<IMyService, MyService>();    //  If someone asks for IMyService give them an MyService instance

**Framework injects the dependencies automatically only when the Interfaces are declared in the Constructor.
The Services are injected through contructors where needed.

eg :-	private readonly IMyService _myService;
		public HomController(IMyService myService){ _myService = myService;}

Now MyService instance is always automatically available whenever the controller is created.

DIP - Dependecy Inversion principle

If there are multiple Implemenatations for 1 Interface, We can use NameServices, keybased factories or IID Injection

*Static Helper Classes can not be injected as they dont have an instance, its better to avoid static classes in DI based.
	rather than Static Classes create injectable Services with Singleton Lifetime if required globally (Logger).

Object/Service Lifetimes  (How long instance of any class persists)
	AddSingleton() - One single instance throughout the Application Lifetime, reused everywhere needed (Logging)  -- Lives for entire application lifetime
	AddScoped() - Each HTTP request creates a new Instance, shared within that req not across.                    -- Lives for HTTP Request Lifetime (Per Request)
	AddTransient() - Creates Instance every time Service is requested, even within same request.                  -- Lives until nobody references it

IServiceProvider.GetService() is the Service Locator Pattern (Anti-pattern/Mistake)
Constructor Injection is preferred because it makes dependencies explicit.

Common mistakes which should be avoided, Injecting Singleton Services in Scoped Contructors could lead to errors unless done carefully using Factories.

What happens internally when ASP.NET resolves a dependency?

UserController Constructor
    └── UserService Constructor
            └── IEmailService   Service Registeration
                    └── EmailService
					
ASP.NET works from the bottom - upward for creating Instances.

Step 1:- Registeration - Before Application can serve a single request, it needs a blueprint. (Application Startup proces, occurs in Program.cs or Startup.cs inside Service Collection)
			builder.Services.AddScoped<IEmailService, EmailService>();
			builder.Services.AddScoped<UserService, IUserService>();
		At this point .Net does not create the object, Instead .Net creates a ServiceDescriptor object for each entry and adds it to a massive internal list (ServiceCollection).
		ServiceDescriptor - It has 3 information - Service Type(Interface - IEmailService), Implemenatation Type(Class_Name - EmailService), and Lifetime (Scoped, Transient, Singleton)
		
		IEmailService -> EmailService (Scoped)   // If someone asks for IEmailService, create EmailService.
		IUserService -> UserService (Scoped)      // If someone asks for IUserService, create UserService.
	At this phase ONLY Instructions are stored, No Instantiation

Step 2 :- Building Service Provider  var app = builder.Build();
	ServiceCollection -> ServiceProvider   // The provider analyzes all registrations and prepares efficient creation plans.
	
Step 3 :- Http Request arrives. UserController is involved.  // Now ASP.NET needs a controller instance.

Step 4 :- DI Container starts examining constructor of Controller -> public UserController(IUserService userService) // UserController requires IUserService
			So before creating UserController: Need IUserService first

Step5 :- Dependency Tree Construction - Container recursively walks the constructor graph :- UserController -> IUserService -> IEmailService   //DI Container checks until it has classes that require nothing else.

Step 6:- At the bottom, it reaches EmailService (which has no dependency). Now It can finally create EmailService Instance.

Step 7:- Now as it has EmailService, It creates UserService then UserController one-by-one.   Instances are created in the reverse order.

Step 8:- Disposal Tracking - (IDisposable) The container keeps track of disposable objects.
	Resources are cleaned automatically.
	
	Request UserController -> Find registration -> Inspect constructor of Implementation -> Find dependencies -> Resolve dependencies recursively -> Create deepest objects first -> Cache according to lifetime -> Return finished object graph


IServiceCollection -> List of ServiceDescriptors -> Build() -> Factories are generated -> IServiceProvider (Root Container) -> Create Scope -> Scoped Container -> Resolve Service

IServiceCollection (builder.services is IServiceCollection) -  A collection where you register all your services.  (MetaData) - List of Service Registerations / ServiceDescriptor.
				actual	IServiceCollection : IList<ServiceDescriptor>   // List of ServiceDescriptor

ServiceDescriptor - A single Service Registeration. Every call like AddScoped(), AddTransient(), AddSingleton() creates a Service Descriptor.
		ServiceDescriptor - It has 3 information - Service Type(Interface - IEmailService), Implemenatation Type(Class_Name - EmailService), and Lifetime (Scoped, Transient, Singleton).

IServiceProvider - The object responsible for creating services. ASP .Net Core converts the IServiceCollection into IServiceProvider.
		IServiceCollection  ->  Build()  -> IServiceProvider 
	Service Provider = Finds Registeration -> Creates Dependencies -> Creates Object -> Returns Object.

Root Container - The main IServiceProvider created when the application starts. var app = builder.Build(); creates the Root provider 
		It is like IServiceProvider rootProvider;
		Application Lifetime

Scoped Container - A child container created from the root container. Because scoped services must be unique per request.
		Request Timeline

Why can't Scoped service be injected into Singleton?
	A Singleton lives longer than a Scoped service, so a Singleton cannot safely hold a reference to a Scoped object.

	If We really have to inject Scoped Service in Singleton, Don't inject the Scoped Service directly, instead inject 'IServiceScopeFactory' or 'IServiceProvider' and create a Scope when needed.

	private readonly IServiceScopeFactory _scopeFactory;
    public ReportService(IServiceScopeFactory scopeFactory) {
        _scopeFactory = scopeFactory;
    }
    public void GenerateReport() {
        using var scope = _scopeFactory.CreateScope();
        var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
    }
	Singleton -> Temporary Scopes -> Scoped DbContext
	
Factory - An Object whose job is to create another Object
	var service = new EmailService(); // Factory converts to var service = factory.Create();  --  The creation logic is hidden inside the factory.
	Sometimes the DI container cannot simply create an object using constructor injection.
	
	ASP.NET Core uses factories internally all the time.
		services.AddScoped<IEmailService, EmailService>();    ---- The container effectively builds a factory behind the scenes.
	Every registration becomes an object-creation factory.
	
		services.AddSingleton<IEmailService>(provider =>   -- Here provider => lambda function is literally a factory
		{
			return new EmailService(
				"my-api-key"
			);
		});
	
	** 'Dependency Injection delivers objects. Factory Pattern creates objects.'

Clean Architecture
	It is a software design approach that separated concerns by organizing code into layers.
	Typically Domain, Application, DataAccess, Infrastructure.
	It promotes Testability, Flexibility and Maintainability by decoupling business logic from infrastructure and frameworks.

Domain Layer - It contains core business models and the interfaces.  (Data Access and Repository)
Application Layer - Use cases are defined, DTOs and Services which have the actual business logic. (Application and Business)
Infrastructure Layer - It handles the Database, external APIs and other outside Services.
Presentation Layer - It is the WebAPI or the User Interface which interacts with the end-user.  (Controller)
App.Application, App.Domain, App.Infrastructure, App.WebAPI.

Dependency Inversion principle - eg - Domain Layer has the Interface IProductRepository and the Infrastructure Layer implements them.

Domain Driven Design - Modeling Business rules and behaviours in the domain layer. 
	When we start with the business/domain, rather than starting with databases, controllers, APIs, or frameworks.
	Build the software around the business rules and concepts that matter to the business.
	Clean Architecture provides structure to implement DDD effectively.

JWT Token Authentication and Role Based Authorization
It is a compact self-contained way of transmitting user identity between client and server.
In ASP.Net core we use JWT as it is stateless authentication.

Token generation typically occurs in a login or authentication method, 
when a user's credential are verified 
Start by using the JWTSecurityTokenHandler
[Authorize(Roles = "Admin")]

Tokens are stored in local storage or session storage.
It is sent with every API Request via Authentication Header: Bearer Token
Tokens are short-lived.
There is a Refresh Token strategy, when token expires user requests for a new access token (Refresh endpoint)

Access Tokens are short lived (15mins). So that if someone steals the tokens, he does not have access for very long.
But the users access also gets removed after 15 mins. They should not login again and use.
Refresh Token provides new Access Token. When the User does the Authentication then it returns Access Token + Refresh Token.

JWT itself is neither authentication nor authorization. It is a token format that can carry identity and permission information.

JWT (JSON Web Token) Token based Authentication via UseAddAuthentication(), UseAuthorization().
For Authorization, we can use Roles and Policies with [Authorize] attr on controllers and Services.   // [Authorize(Permissions.Admin)]

	JWT is STATELESS. JWT is slef-contained so there is no need of Session Storage on Server.
		The token itself contains the information needed to identify and authenticate the user, along with a signature that allows the server to verify that the token hasn't been tampered with.
	
Traditionally Browser sent Username/Password to Server, Server created Sessions, Stores Session in DB. Browser stores Cookie: (SessionId). Every request will have this Cookie: (SessionId).
If there are multiple servers, Which server has the Session. No Idea. It becomes very complex.
	Browser -(Username/Password)-> Server, Server creates Session (SessionId: abc123), Stores abc123 -> User in DB. Browser stores Cookie:abc123 and sends this with every req. Then Server looks up for the Session.

JWT solves this issue.
JWT creates a Self-Contained Token. A compact format for securely transmitting claims.  (eyJhbGciOiJIUzI1Ni...)

JWT has 3 parts: (xxxx.yyyy.zzzz)   (Header.Payload.Signature)
	-> Header  - 2 parts -> Algorithm Used & Type { "alg": "HS256", "typ": "JWT" }
	-> Payload - Contains Claims about the User -> { "sub": "123", "name": "John", "role": "Admin" } ->  Subject/UserId, UserName, Email, Expiration, IssuedAt, Role
	-> Signature - Generated using Encoded Header + Encoded Payload + Secret Key (It takes the algorithm specified in Header and takes Header,Payload and Secret key and Signs it).
	
	If Payload changes (someone tampers values), Signature won't match, Server rejects the Token.
	
	JWT is usually encoded, not encrypted.  ( Encoding = changing the representation of data. Encryption = hiding the data using a secret/key. )
	Anyone can decode the Header & Payload. But they cannot modify it without breaking the signature.
	
User Logs In -- (Username/Password)--> Server Validates the Credentials --> Server creates JWT --> Returns the Token --> Client Stores the Token 
Requests will have Authorization Header Bearer ey.....
Whoever has the Token, can access. Possession grants Access.

Access Token - Short lifetime (15 min).
Refresh Token - Long lifetime (30 days).  -> Used to obtain new Access Tokens, When the Access Token expires, Client sends POST Refresh API and receives a new Access token.

OAuth: Authorization   - OAuth is an authorization framework.  (Any Application needs access to Google Drive(any third application access),
		We can not share our Google Password with the Application, Instead Google provides Access Token to the APP if User Allows.
			(So that Application does not get to know the Password)). It does not have Identity or any information of the User only a token for access.

OIDC: Authentication - OpenID Connect is an identity layer built on top of OAuth 2.0 that provides authentication. This includes the Identity of the User. Who is the User loggedIn.

OAuth Authorization Code Flow - User Clicks Login with Google -> Redirect: Client > Google Login -> User Authenticates -> Google Asks Allow App to access profile -> User Approves -> Google return Authorization Code (Access Token) -> Client exchanges code for Access Tokens -> Client has Access to Google APIs.
OAuth only provides access token to the application. A way to get permission to access somebody else's resources without knowing their password.

OAuth Scopes - Scopes Limit Permissions (read_profile, read_email, read_drive). OAuth Scopes are used to Grant minimum permissions (Only what is required).

OIDC - Open ID Connect - This is an Identity Layer built on top of OAuth 2.0 that provides Authentication.  (OAuth + Identity Information)

Why OIDC ? - OAuth only tells What access is to be given to the Application. App does not know Who the User is ? OIDC solves this issue, It adds Identity with the Access Token.
 
OAuth tells App can access API, OIDC adds Identity. OIDC adds Identity Token (Access Token + Identity Token(JWT)).
When we click Continue with Google we are actually using OIDC.
OIDC extends OAuth by adding authentication and identity information through an ID token.

OAuth 2.0 is an authorization framework used to grant an application limited access to a user's resources without sharing credentials.
OIDC (OpenID Connect) is an authentication layer built on top of OAuth 2.0 that adds identity information through an ID Token.
OAuth answers "What can the application access?" while OIDC answers "Who is the user?"

Why not use OAuth Access tokens for Identity ? (As OAuth Token can have User Information)  
	Earlier OAuth was used for Access and Identity as well. But it got very messy as the format was not standardized. Every provider did it differently.
	OIDC standardized the Process, Endpoint and Format.
	Because access tokens are intended for: Resource Servers (APIs)
	while ID tokens are intended for: Client Applications            (They are intended for different Audiences)
		Access Token -> Google Drive API
		ID Token -> Your Application
	
Scenario 1 :- Traditional Login - Imagine If a website has its own LogIn. User enters his Credentials. Website checks its Database, Validates the User from User Table.
		NO OIDC. NO GOOGLE NOTHING.  INDEPENDANT LOGIN.

Change Tracking :- It keeps a track of what entities it loaded and detect what changed so it can generate the correct SQL statements when you call SaveChanges().
	Drives the changes when SaveChanges() is called.

These are the Entity States - 
-> Tracked - By Default when an Entity is fetched it is Tracked. EF remembers it.
		var employee = context.Employees.First();
-> Detached - Entity is not being tracked. EF ignores it.  (AsNoTracking())   -- When Data only needs to be displayed and not updated (Only Read Queries), No Intentions of SaveChanges()
		var employee = context.Employees.AsNoTracking().First();       		  -- Now EF does NOT track. No Change Tracker Entry
			** Memory usage is lower. Performance is better.
-> Added - New Entity is added to the Content.  - context.Employees.Add(employee); 
		Meaning Insert this row  - INSERT INTO Employees(...)
-> Unchanged - Loaded from database.  - var employee = context.Employees.First();
		Row has No Changes
-> Modified -  Some of the columns have been updated - employee.Name = "David";
		Update Row 
-> Deleted - Any Existing Entity is removed from the Content.  - context.Remove(employee);
		Delete Row

EF Stores Original Values and Current Values for Comparision.

What happens when SaveChanges() is called?
	EF Core loads some Entity before SaveChanges is called.
		var employee = context.Employees.First(e => e.Id == 1);  -- EF Core loads the entity and stores it in an internal structure called the Change Tracker.
	Now if any of the Value is updated for that entity.
		employee.Salary = 7000;  -- Value updated to 7000
	When SaveChanges() is called.
		 Change Tracker stores the updated value and previous value as well and compares the both and creates list of changes to be done.
			// 	According to the list of changes the Change Tracker generates the SQL Statement, to actually update the value for the entity.
		UPDATE Employees SET Salary = 7000 WHERE Id = 1;



Transactions using var transaction = await _context.Database.BeginTransactionAsync();
Transactions - A transaction is a way to group multiple database operations into a single logical unit of work.
	Never a half-completed operation. All or nothing. ATOMICITY

Why transactions?
	If we are Sending Money from A to B. Money got deducted from A, after that Server Crashed. B never recieved the money. Money Disappeared.
	Transaction helps create a Temporary workspace, Changes are made inside this Workspace. until await transaction.CommitAsync(); is called.
	Now after this CommitAsync(), the real database is permanently updated.      --- Commit means Looks Good, Make it Permanent.
	
Rollback Transactions - Forget everything I did in this transaction. (If there was a failure in between the process or Server Crashed or any other possible issue).
	Actual Database is never updated with the new Values or updates.
	
	await context.SaveChangesAsync();  ---  EF Core automatically creates a transaction for that save operation.
	
	**EF Core has built-in transactions, but there are some cases when sometimes you need multiple operations to succeed together.

Nested transactions - A transaction inside another transaction. Most databases do not support true nested transactions.
	
ACID Properties
	Every database transaction is expected to follow four principles:
		Atomicity   - All or Nothing
		Consistency - The Database must remain valid.  (Rules are preserved.)
		Isolation   - Transactions should not interfere with each other. (All requests must be isolated, Each transaction behaves as if it's running alone)
		Durability  - Once committed, Data is permanent. Even if the Server crashes immediately after the commit.

What if two users update same record simultaneously?  Concurrency

Asynchronous Model - 
Parallel Execution, Multiple Threads are available, Multiple Instructions get executed simulatenously on different threads.

Threads can be used to execute tasks, workitems, async I/O, timers.

Async and Await :-
To write Non-Blocking code that reads like synchronous code.
It allows I/O bound operations like calling a DB, reading a file or making HTTP call to run asynchronously.
Instead of a thread sitting idle, waiting for a DB to respond. The Thread is freed up to serve other users which massively improves the scalability of API.

When a method marked with Async hits an await, it does not block the thread.
Instead the compiler generates a hidden state machine (IAsyncStateMachine).
It pauses the execution, yields the thread back to the thread-pool and once the awaited task completes, State machine resumes the execution exactly where it left off.

Mistakes to avoid :- 
Never use .Result() or .Wait() - It makes the thread wait synchronously for an asynchronous process, which causes Thread Pool Starvation.
Fire and Forget Tasks - Calling an async method but not putting an await while calling.

public async Task Function();
Dont use async void. Always use async Tasks while method creation. Method should always return a Task.
If it is void, there is no way User can track the completion of the Method/Task. 
If an exception is thrown inside async void, it is not caught.

ConfigureAwait(false);
It tells the compiler that the continuation of the async method does not need to resume on the exact application thread context it started.
In Modern ASP.Net Core, there is no synchronizationContext, so it does not prevent Deadlocks anymore.
	SynchronizationContext in .NET/C#, it is a mechanism that helps code run on the correct thread or execution environment.

Task - A standard task is reference type, it allocates the memory on heap, which has to be cleaned up by GarbageCollector at some point.
ValueTask - It is a struct, it prevents unnecessary memory allocation. Stack Allocation (Zero GC pressure)
If you have method which returns data immediately, like fetching from in-memory cache.
Task (Unit of Work) - When a Task object is created and started, the CLR creates a thread for executing the task.
Task represents asynchronous operation. It may or may not use a thread.

For Heavy CPU bound work - use Task.Run() to explicitly offload complex functionality to background worker thread so it does not freeze the main calling thread.

Task.Run() = CPU-bound work
async/await = I/O-bound work

Anti-Pattern - Never use Task.Run() in APIs.
ASP.Net Core already runs on Thread Pool. If Task.Run() is used inside an API, it literally steals a second thread from the pool just to offload work from the first thread.
Under Heavy-traffic it would exhaust the thread-pool and crash the Server.

Concurrently calling multiple external APIs
var task1 = _api.GetUserAsync();

await Taks.WhenAll(Task1, Task2);   - Runs both concurrently, waits for both to get completed
Instead of awaiting for 1st task and then awaiting for 2nd task. It starts both tasks immediately and store them in variables.
Then pass both to Task.WhenAll(), It runs them in parallel.

Task.WhenAll() is asynchronous :- it returns a task that you can await, keeping thread free.
		It is used when making a known number of independent asynchronous I/O operations, such as calling 2–10 external APIs.
Task.WaitAll() is synchronous :- it physically blocks the current thread until all the tasks are complete.

LINQ - Langauge Integrated Query
Unified way of querying. It allows you to write clean, type-safe, and readable queries against any data source using a unified syntax.
It is used to generate highly optimized SQL Statements

LINQ works via a provider model. The C# code written is translated by a LINQ Provider into a format the underlying data sources understand.
-> LINQ to Objects: Used to query in-memory collections like List<T>, Dictionary<T>, or arrays.
-> LINQ to Entities (EF Core): Translates your C# LINQ expressions into highly optimized SQL queries and executes them on a database server (like SQL Server, PostgreSQL, etc.).
-> LINQ to XML (System.Xml.Linq): Used to query and manipulate XML documents efficiently.

Syntaxes :-
1. Query Syntax (Declarative)
	List<int> numbers = new List<int> { 1, 2, 3, 4, 5, 6 };

	var evenNumbers = from num in numbers
						where num % 2 == 0
						select num;
						
2. Method Syntax (Fluent / Lambda)
	var evenNumbers = numbers.Where(num => num % 2 == 0);
	
Built-in operators
-> Filtering (Where) - Filters a collection based on a condition.
	var VIPs = customers.Where(c => c.TotalSpent > 1000);
-> Projection (Select, SelectMany) - Transforms elements into a new shape or extracts specific properties.
	List<string> emails = customers.Select(c => c.Email).ToList();
-> Ordering (OrderBy, OrderByDescending, ThenBy) - Sorts the data
	var sortedEmployees = employees.OrderBy(e => e.LastName).ThenBy(e => e.FirstName);
-> Elements (First, FirstOrDefault, SingleOrDefault) - Extracts a specific single element from a collection.
	First(): Returns the first item. Throws an exception if the list is empty.
	FirstOrDefault(): Returns the first item, or null (default) if empty. (Highly Recommended)
		var user = users.FirstOrDefault(u => u.Id == 42);
-> Aggregation (Sum, Min, Max, Average, Count) - Performs math calculations over the collection.
	int totalInventory = products.Sum(p => p.UnitsInStock);
-> Quantifiers (Any, All) - Returns a boolean check based on your criteria.
	bool hasOverdueInvoices = invoices.Any(i => i.IsOverdue);
	
Deferred Execution (Lazy Evaluation)
When we write a LINQ query, it does not run immediately. It merely stores the instructions on how to execute the query.
The query is only executed when we actually try to read the data.
	// Query is defined here, but NOT executed yet
	var query = list.Where(x => x > 1); 
	// The query actually RUNS here because we call ToList()
	var result = query.ToList();
	
Greedy Operators - .ToList(). .ToArray(), .ToDictionary(), FirstOrDefault(), Count()

In .NET, IEnumerable and IQueryable are two of the most fundamental interfaces used to work with collections of data.
-> Use IEnumerable for data sitting in your local machine's memory (RAM).  LINQ operations are generally performed in .NET/application memory.Give me objects/elements and I'll use .NET to process them.
		Give me objects/elements and I'll use .NET to process them.
			_dbContext.Employees.AsEnumerable().Where(e => e.Salary > 100000).Take(10).ToList();    Where and Take are executed by .NET against the sequence being enumerated.

-> Use IQueryable for data sitting out in a remote database (SQL Server, PostgreSQL, etc.)
		LINQ operations can be represented as expression trees and translated by the query provider, such as EF Core, into SQL.

IEnumerable (System.Collections.Generic) - every data collection in C# (List<T>, Array, Dictionary<T>) implements IEnumerable.
	IEnumerable executes queries using LINQ to Objects. It acts as a forward-only reader over an in-memory collection. 
	When you filter an IEnumerable, it pulls all the data into memory first, and then filters it locally using C# code.
		// Imagine this table has 1,000,000 rows in the database
		IEnumerable<Employee> employees = _dbContext.Employees.AsEnumerable();
		// This filtering happens entirely in your Application's RAM!
		var highEarners = employees.Where(e => e.Salary > 100000).Take(10).ToList();
		
IQueryable (System.Linq) - It inherits from IEnumerable, but it is designed specifically for remote data sources.
	IQueryable executes queries using LINQ to Entities. Instead of holding raw data, it holds an Expression Tree—which is a blueprint of what you want to find.
		It represents a query that can be translated by a provider
	When you apply filters like .Where() or .Take(), it doesn't run them immediately. It converts the C# Logic into SQL Query. The database engine executes the filter, 
	and only the matching results are sent back over the network.
		// This creates an Expression Tree blueprint (0 rows downloaded yet)
		IQueryable<Employee> employees = _dbContext.Employees.AsQueryable();
		// The query is translated into SQL and executed on the database server!
		var highEarners = employees.Where(e => e.Salary > 100000).Take(10).ToList();     // SELECT TOP 10 * FROM [Employees] WHERE [Salary] > 100000



CQRS - Command Query Responsibility Segregation.
	Separate operations that change state from operations that only read state.
		OrderCommand - Write Model ➜ Change Data
		OrderQuery - Read Model ➜ Read Data

	A Command expresses an intention to change something. A command changes state and usually doesn't return the requested data.
	A Query asks for information without changing state.
		Same Database is used.
	Command Handler - Command Orchestration.  What should happen when Command arrives?  It can coordinate validation, authorization, transactions, and domain services.
	
	Don't force the same model to serve both responsibilities when separating them provides a useful architectural benefit.

	** CQRS is not automatically better. For a simple CRUD application, separating commands and queries can add unnecessary complexity. It's most useful when the read and write sides have substantially different requirements.


Design Patterns :- (Must Patterns)
	Design Patterns provide proven standardized soltuions to common architectural problems. They drastically improve Code Reusability, Testability and Maintainability.
	
	➜ Repository Pattern :- It is essential for abstracting data access logic. Instead of Tightly Coupling our services to Entity Framework, Use an interface for the Repository.
			Interface of repository make Mocking data for Unit Testing easier and allows us to swap the persistence implementation if business requirements change.
	
	What is Unit of Work pattern and Repository ?
		We use Unit of Work and Repository pattern together as they complement each other perfectly.
		A Repository handles data operations for one single entity. A Unit of Work co-ordinates transactions across multiple repositories.
			In complex domains we can use IUnitOfWork.SaveChangesAsync() to ensure all changes across multiple tables are commited in a single, safe database transaction.
	
	➜ Singleton Pattern :- This ensures a class has only one instance throughout entire application Lifetime. instead of writing complex custom singleton classes. 	
				We register the service using service.AddSingleton<ILoggingService, LoggingService>();
			Perfect for Stateless Service or share in-memory caches.
	
	➜ Factory Pattern :- It creates Objects without exposing the complex creation logic to the client. It keeps Controller unaware of the complex condition based creation logic.
	
	➜ Strategy pattern :- Its good for encapsulating Algorithms. Instead of writing massive if else blocks, we inject a specific strategy. Follows OCP.

	➜ Mediator Pattern :- (CQRS) Mediator pattern acts as a Central Hub for Communication. With the Mediator Library, We implement CQRS by separating commands and queries.
							Controller sends a Command / Query and MediatR routes directly to that specific Handler. It decouples our API from our business logic.
	
	➜ Decorator Pattern :- It lets us attach a new behaviors dynamically without changing the code.
								services.Decorate<IEmailService, LoggingEmailService>();    // DI Setup using Scrutor Library, 
									We wrap inside a LoggingEmailService, Logging or retries can now be added to EmailService without ever modifying the actual Service.
	
	➜ Adapter Pattern :- It is a bridge between two incompatible Interfaces. When consuming a third-party API to get a response and align it to the expectation of our own Service.
							Adapter makes the response from external API in the same format as that of our Service.
	
	➜ Null Object Pattern :- Instead of returning Null and forcing the Consumer to write Null-Checks, We return a no-op Object or an empty collection.
								return new NoOpLogger();  				// instead of returning Null
								return Enumerable.Empty<Product>();		// instead of returning Emptylist.
	
	➜ Builder Pattern :- It separates the construction of a complex object from its representation. (Fluent APIs)
							Instead of a constructor with 15 parameters, we chain methods together like var order = new OrderBuilder().withCustomer("John Doe").AddItems(cartItems).Build();
								It ensures Object is build in a valid state step by step.
	
	➜ Chain of responsibility :- (BackBone of ASP .Net Core Middleware) In this pattern a Request processes through a chain of Handlers. 
									Each Middleware processes the request and then passes the request to the next Middleware in the pipeline/chain. 
	
	➜ Options Pattern :- Options pattern strongly types our AppSettings.Josn configurations. 
							Instead of Injecting IConfiguration and searching for strings, We map the JSON to a C# Class. We inject IOptions into our Services.
	
	➜ Facade Pattern :- When the API becomes too complex for a client call. Facade Pattern provides a simplified interface to a complex system. Client is only exposed to a single endpoint performing all complex logic.
	
	➜ Proxy Pattern :- It acts as a Placeholder or a Surrogate for another Object. CachingProxy 
	
	➜ Observer Pattern :- It defines a one-to-many relationship where objects are notified of State changes. While we traditionally use C# events. 
							In Modern Apps we use Pub/Sub message Bus. When an Event completes, system publishes an Event. Multiple bg services Observe or subscribe to event and react.
							Architecture is highly decoupled.
	
	➜ Circuit Breaker Pattern :- Stops an application from repeatedly trying to execute an operation thats likely to fail. Using Polly and .Net
	
	➜ State Pattern :- It allows an Object to alter its behavior when its internal state changes

      A        B
      |        |
   C v1.0    C v2.0

Depending on the ecosystem, it might:
- Choose one version and use it for everything.
- Install both versions.
- Upgrade/downgrade one dependency.
- Fail because the version requirements are incompatible.

If A requires CommonLib >=1.0,<2.0 while B requires CommonLib >=2.0, there may be no single version that satisfies both.

Explain Circuit Breaker Pattern with a real-world example.
	Circuit Breaker is a resilience pattern used in distributed systems to prevent repeated calls to an unhealthy downstream service. It has 3 states: Closed, Open, and Half-Open.
	In the Closed state, requests flow normally. If failures exceed a configured threshold, the circuit Opens and subsequent calls fail fast without calling the downstream service. 
	After a cooldown period, it moves to Half-Open and allows a few test requests.
	
	If a downstream service keeps failing, the circuit breaker stops sending requests to it temporarily.
	
	Without a Circuit breaker, new requests will repeatedly be called to the Service and it would fail each and every time until the Service is up and running.
	Threads and resources are consumed.

Difference between Synchronous and Asynchronous Communication.
	Synchronous : Wait for the response, Once response is received then proceed further with the execution.  	HTTP, REST, gRPC    			High Coupling
	Asynchronous: Send the Request and continue with the execution, Once request completes it informs.		Queue, Message/Event Brokers		Low Coupling

	await httpClient.GetAsync(url); This is asynchronous programming, because the thread doesn't need to block while waiting for I/O, but it's still Synchronous communication.
		Thread is free to do other work, It is not Blocked.
	
	Use synchronous communication when:  In synchronous communication, the caller sends a request and waits for the receiver's response before continuing. REST and gRPC are common examples
		You need an immediate response.
		The caller cannot continue without the result.
		You need a simple request/response interaction.
		
	Use asynchronous communication when:  In asynchronous communication, the sender publishes a message or event and doesn't wait for the consumer to finish processing it. Kafka, RabbitMQ, Service Bus
		The work can happen in the background.
		You don't need an immediate result.
		Reduce coupling between services.
	When Async and await are used in the APIs they are used for making the flow Synchronous, else if we are using some third-party API and we dont use Async and await. Execution would complete before we receive response from the external API


Why does Async Await does not automatically create a new thread ?
	Because async/await is primarily about not blocking a thread while waiting, not about creating threads.
	There is no need to create another thread while waiting for the HTTP response.
	
	But when does a new thread get created? This is where people often confuse async with Task.Run.    Async/Await Usually doesn't require a new thread for the waiting.
	Task.Run explicitly schedules the CPU-bound work on the ThreadPool.
	Async/await is designed to avoid blocking threads, especially during I/O operations.

What causes thread pool starvation ?
	Thread Pool Starvation happens when all available ThreadPool threads are busy for too long, so new work has to wait for a ThreadPool thread to become available.
		• Blocking on async code. Not using await for an async method.
		• Synchronous database calls. If the database takes 5 seconds to respond, the request thread can remain occupied during that wait.
		• Synchronous HTTP calls. External API call without async/await.
